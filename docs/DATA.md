# 데이터: 무엇을, 어디에, 어떻게 저장하나

## 저장 계층
| 계층 | 위치 | 내용 | git |
|---|---|---|---|
| ① 원본 스냅샷 | `data/raw/<sha1(url)>.body.gz` + `.meta.json` | 받은 HTML/JSON 원문 그대로 (gzip). ETag, Last-Modified, 수집 시각 | 제외 |
| ② 정제 원문 | `data/jobs.sqlite` → `jobs` | 공고별 텍스트(본문, 자격요건, 우대: HTML 태그만 제거), 메타, 상태, content_hash | 제외 |
| ③ 규칙 추출 | `jobs` 컬럼 | 기술, 최소 경력, 코테·과제 여부 | 제외 |
| ④ LLM 해석 | `job_insights` | 팀 문제, 축별 항목과 **원문 인용**, 경계 신호, 전형, 단계 단서 | 제외 |
| ⑤ 집계 | `data/stats/*.json`, `data/personas/*.json` | 통계, 페르소나 수치 (원문 일부 인용 포함) | **git 제외** (각자 크롤링해서 생성) |
| ⑥ 생성물 | `personas/stage-*.md`, `profiles/<id>/reviews/` | 카드, 리뷰 | git 제외 (카드는 각자 생성, 리뷰는 프로필 폴더) |

## 원문을 저장해야 하나? 꼭 가공해야 하나?
**지금 구조는 원문(①②)과 가공본(③④⑤)을 둘 다 저장합니다.** 이 방식을 권장하는 이유는 아래와 같습니다.

| 선택 | 장점 | 단점 |
|---|---|---|
| 원문만 저장 | 정보 손실 없음. 추출 규칙이 나아지면 언제든 재처리 | 쓸 때마다 다시 가공해야 함. LLM에 원문을 반복해서 넣으면 토큰이 커짐 |
| 가공본만 저장 | 작고 빠름. 리뷰에 바로 사용 | 추출기·프롬프트 버그가 영구 손실이 됨(재해석 불가). 인용 검증 불가. 사이트에서 공고가 내려가면 복구 불가 |
| **둘 다 (현재)** | **재처리 가능**(규칙 개선, 프롬프트 버전 변경 시 원문에서 다시). **인용 검증 가능**(해석의 원문 인용을 원문과 대조). **감사 가능**(어떤 공고에서 나온 판단인지). 변경 감지(해시 비교) | 저장 공간 사용 (원본 HTML이 큼: 압축 전 530페이지 115MB). 원문 재배포 위험 |

이번 작업에서 실제로 원문 덕분에 할 수 있었던 일들입니다.
- 쿠팡 공고가 잘렸던 문제를 원문에서 9건만 다시 해석해 고쳤습니다.
- 인용 검증을 앞 60자 비교에서 전문 대조로 강화한 뒤, 저장된 해석 264건을 **LLM 호출 없이** 원문과 다시 대조했습니다.
- 무신사 제목 변경을 원문 비교로 원인 분석했습니다.

가공만 저장했다면 셋 다 불가능했습니다.

## 저장 정책
- **원본 스냅샷은 gzip으로 압축**합니다(`crawler/fetch.py`). HTML은 압축률이 높습니다. 기존 `.body` 파일은 읽을 때 호환되고, 다시 받을 때 압축본으로 바뀝니다.
- **보존 기간 (권장)**
  - 모집 종료(`status=closed`) 후 90일이 지난 공고의 원본 스냅샷은 지워도 됩니다. ②의 정제 원문과 ④의 해석은 남깁니다.
  - 아직 자동화하지 않았습니다. 필요하면 정리 스크립트를 추가합니다.
- **git 제외**: ①~⑥ 전부와 sqlite 임시 파일(`-wal`, `-shm`). 공개 저장소에는 공고에서 나온 데이터를 싣지 않는다(2026-10-26 결정). 각자 `AGENTS.md` 0절 순서로 만든다.
- 멘토 원칙: 공개 자료만 `mentors/principles.yaml`. 직접 받은 조언·유료 자료 요약은 `profiles/<id>/mentors/principles.yaml`.
- **재배포 금지**
  - 원문은 개인 연구용으로만 씁니다.
  - 서비스로 확장할 때는 원문을 화면에 그대로 다시 보여 주지 말고, 해석 결과와 짧은 인용과 원문 링크만 보여 주는 것을 전제로 합니다.
  - 상업적 이용은 각 사이트 약관을 별도로 확인해야 하고, 공식 API를 우선합니다.

## 출처별 사용 범위
| 출처 (`jobs.source`) | 방식 | 사용 범위 |
|---|---|---|
| `rallit` | 공개 sitemap + 페이지 | 개인 분석. 서비스 전 이용 조건 재확인 |
| `ats_greenhouse`, `ats_lever`, `ats_greeting` | 회사가 공개한 채용 API | 개인 분석·서비스 모두 상대적으로 안전 |
| `saramin` | 사람인 공식 오픈 API | API 이용 조건 범위 안에서 |
| `saramin_web` | 사람인 웹 (robots.txt 허용 경로, API 키 승인 전 임시) | **개인 분석 전용.** 서비스용 통계·페르소나에는 쓰지 않는다. 키가 생기면 자동으로 멈춘다 |

- 채용공고 크롤링은 사람인 대 잡코리아 판결(부정경쟁·데이터베이스권 침해)이 있는 분야다. 서비스로 만들 때는 공식 API와 회사 공개 API 데이터만 남긴다.
- 봇 차단(403, 챌린지)은 우회하지 않는다.

## 개인 데이터
- 지원자 데이터는 `profiles/<id>/`에 둡니다. 엔진 git에서 제외되고, 폴더마다 자체 git을 둡니다.
- 외부 LLM으로 보내기 전에 `coach/redact.py`로 개인정보를 가립니다(이메일, 전화, 주민번호, 주소, 이름).
- 이력서에서 파생된 후보자 프로필 캐시는 `data/cache/candidates/`에 있습니다(git 제외).
