# 공통 채점 앵커와 피드백 품질 규칙 (모든 페르소나와 리뷰어에 적용)

## 점수 앵커 (기준별 0~5)
| 점수 | 의미 | 판정 예 ("성능 개선" 기준) |
|---|---|---|
| 0 | 해당 내용이 없음 | 성능 관련 언급 없음 |
| 1 | 키워드만 있음 | "성능 최적화 경험" |
| 2 | 무엇을 했는지 행동은 있으나 결과가 없음 | "Redis 캐시를 적용함" |
| 3 | 결과 수치는 있으나 측정 방법·조건이 없음 | "응답 속도 70% 개선" |
| 4 | 수치 + 측정 방법·조건 + 내 역할이 분명함 | "p95 800→240ms(k6, 동시 200), 캐시 키 설계와 무효화 전략을 직접 설계" |
| 5 | 4 + 의사결정 근거·트레이드오프·후속 효과까지 설명됨 | 4에 더해 "write-through 대신 TTL+이벤트 무효화를 택한 이유, 정합성 리스크 대응, 이후 DB CPU 40% 감소" |

- 기준마다 이 앵커에 비춰 **왜 그 점수인지** 한 줄로 적는다. 다음 점수로 가려면 무엇이 필요한지도 적는다.
- 점수는 관대하게 주지 않는다. 의심스러우면 낮은 쪽을 택한다. 4점 이상에는 원문 인용이 필요하다.

## 지적(코멘트) 하나가 갖춰야 할 4요소
1. **원문 인용**: 이력서·답변에서 해당 문장을 그대로 가져온다. 위치를 알 수 있게 쓴다.
2. **문제**: 무엇이 왜 약한지. 앵커 기준이나 공고 요건과 비교한다.
3. **수정안**: 바로 바꿔 쓸 수 있는 문장. 모르는 수치는 지어내지 않고 `[측정값]`처럼 자리표시로 둔다.
4. **근거**: `[통계: <stage> <skill> N%]`, `[요건: "<공고 원문 문장>" (uid)]`, `[멘토: 파일#원칙N]`, `[앵커: 기준 N점 정의]` 중 하나 이상. 없으면 "의견"이라고 쓴다.

4요소 중 하나라도 빠진 지적은 제출하지 않는다.

## 근거 출처 유형 (모든 판단에 하나 이상 표시 — 사용자가 "어디서 나온 판단인지" 구분할 수 있게)
| 태그 | 의미 | 신뢰도 |
|---|---|---|
| `[공고]` | 특정 공고에 **명시된** 요구 (원문 인용 + uid 필수) | 높음 |
| `[통계]` | 여러 공고의 집계 수치 (`data/stats`, `data/personas`의 비율·lift) | 높음 (표본 수 함께 표기) |
| `[멘토]` | 멘토 원칙 카드 (`mentors/*.md#원칙N`) — 경험 기반 평가 기준 | 중간 |
| `[단계추정]` | 회사 성장 단계에서 추론한 평가 성향 (페르소나 contrast·경계 신호 중 공고에 직접 없는 것) | 낮음 — "가설"로 표현 |
| `[의견]` | 모델 자체 판단 | 낮음 |

- 결과 끝에 출처 유형 분포를 한 줄로 적는다(예: 공고 6 · 통계 3 · 멘토 2 · 단계추정 1 · 의견 1).
- `[단계추정]`·`[의견]`만으로 "반드시 고쳐야 한다"고 단정하지 않는다. "~일 가능성" 수준으로 쓴다.

## 아첨 방지
- 약점은 **반드시 3개 이상** 쓴다. 그중 1개는 "가장 큰 레버"로 꼽는다.
- 근거 없는 칭찬은 금지한다. 강점을 말할 때도 원문과 근거를 붙인다.
- "수치를 넣으세요", "구체적으로 쓰세요" 같은 **일반론은 금지**한다. 반드시 해당 문장에 맞춘 수정안을 준다.
- 사용자에게 듣기 좋은 결론으로 바꾸지 않는다. 시장 통계와 어긋나는 사용자 선호가 있으면 그대로 짚는다.

## 사실성
- 이력서에 없는 경험이나 수치를 사용자가 한 것처럼 쓰지 않는다.
- 공고 요건을 인용할 때는 `data/stats/<stage>.json`의 `sample_requirements`나 sqlite 원문에서 그대로 가져온다. 요약하거나 의역한 것을 인용으로 쓰지 않는다.
